## 2. 온체인 옵션이 어려운 진짜 이유

### 처음 제기한 3가지 문제
1. 정산가 오라클 조작 가능성
2. 포트폴리오 마진 계산 불가
3. Vol Surface 실시간 유지 비용

### 논의 후 재정리
- **동적헤지 이산화는 TradFi도 동일** — 온체인만의 문제 아님
- **HL perp 가격 조작은 사실상 불가** — 유동성이 충분히 깊어서 조작이 아니라 진짜 시장 움직임으로 봐야 함. Deribit Index보다 조작 저항성 더 높을 수 있음
- **마진 계산 자체는 어렵지 않음** — TradFi에서도 SPAN(16개 시나리오 배치), ISDA CSA(일별 VM 교환) 방식으로 오프체인에서 계산 후 결과만 적용

### 진짜 병목 (압축)
| 문제 | 내용 |
|------|------|
| 정산가 오라클 | HL에서는 사실상 해결 |
| 포트폴리오 마진 | 계산 자체보다 "누가 언제 계산하냐"가 문제. L1 네이티브 vs HyperEVM 서드파티 |
| Vol Surface | AMM 아닌 CLOB이라 HL에서는 가능성 있음 |

### 마진 계산 오프체인 처리 시 문제
- 오프체인 엔진 계산 결과를 온체인이 검증할 방법 없음
- 해결 방향: ZK proof(복잡), 오라클 네트워크(dispute window 문제), HL validator 직접 계산(L1 네이티브)
- **Aevo가 현재 가장 근접한 구현체** — 오프체인 매칭 + 온체인 정산으로 타협, 완전한 trustless는 포기

## 3. 바이너리 옵션 + 예측시장 구조

### 해결되는 것
- 마진/Greeks 문제 → 사전 프리미엄 전액 납입으로 사라짐
- 포트폴리오 마진 → 애초에 불필요
- 정산 메커니즘 → YES/NO로 단순화

### 근본적으로 안 되는 것
- **가격발견 불가** — 특정 행사가/만기의 점추정만 가능, Vol Surface 형성 불가
- **헤지 수단으로 못 씀** — 행사가 근처에서 델타 스파이크, 실수요자 사용 불가
- **결론**: 옵션의 복잡성을 제거하면 옵션이 존재하는 이유(헤지, vol trading, 가격발견)도 같이 제거됨

## 4. CPMM LP 메커니즘 분석

### 기본 구조
```
x * y = k  (YES토큰 * NO토큰 = 상수)
YES 가격 = y / (x + y)
```

### 확률 0.8 고정 가능한가 (질문 1)
- 가능하지만 LP가 능동적으로 리밸런싱해야 함
- YES 추가 공급 = 만기 YES 확정 시 정산 의무 증가 = 사실상 YES 숏 포지션 누적

### Reserve 필요액 (질문 2)
```
필요 Reserve = 투자자 원금 × (1/확률 - 1)
= 100 × (1/0.8 - 1) = $25
```
- 투자자 $100 → YES 확정 시 $125 지급 → $25 부족분

### 무담보 차입 효과 (질문 3)
| TradFi 용어 | 이 구조 |
|-------------|---------|
| 차입자 | LP |
| 대출자 | YES 베터 |
| 이자율 | 25% (1/p - 1) |
| 담보 | 없음 |

**역설**: LP가 수익을 내려면 실제 확률이 시장 확률(0.8)보다 낮아야 함. 기초 이벤트가 Y=1에 가깝다고 확신하면 LP가 아니라 YES 매수가 맞는 포지션.

## 5. 자금조달 레이어 설계

### 핵심 아이디어
```
예측시장 = 자금조달 레이어
운용 전략 = 수익 레이어
차익 = 운용수익 - 약정수익률
```

### 오프체인 운용의 문제
- Polymarket: 컨트랙트 내 자금 인출 불가
- 자체 컨트랙트 필요하나 → 오프체인 운용 시 "플랫폼이 실질적 차입자" → 유사수신 리스크
- 해결: ZK proof, TEE(SGX), SPV 법인 구조 — 각각 복잡하거나 신뢰 기반

### 온체인 운용으로 해결 (현실적 방향)
```solidity
// 투자자 납입 즉시
aave.supply(USDC, amount);

// 만기 시
aave.withdraw(USDC, amount + interest);
```
- AAVE 예치: 연 5~8%, 완전 자동, trustless
- HL Funding Rate: HyperEVM ↔ L1 분리로 현재 직접 접근 불가 (기술적 병목)
- Pendle 고정금리 YT: 수익률 미리 확정, 정산 단순화

### 부족분 해결
```
YES 베터 $100 + NO 베터 $25 동시 유치
총 $125 운용 → 운용수익은 프로토콜 수수료로 선취
```

### 플랫폼 토큰 역할
- Junior Tranche: 손실 우선 부담, 초과수익 수취
- 초기 유동성 버퍼: 한쪽 베터만 있을 때 임시 채움
- 거버넌스: 탈중앙화 프레이밍 → 규제 방어
- 플라이휠: 수익 → 소각 → 가치 상승 → 유입

**리스크**: Luna-UST처럼 토큰 가치와 지급능력 순환참조 금지. Treasury는 USDC로 충분히 확보.

### 법적 포지셔닝
```
플랫폼 ≠ 대출자
플랫폼 = 프로토콜 개발자 (Uniswap 논리)
온체인 운용 + 컨트랙트 자동실행 → "코드만 배포했을 뿐"
```
오프체인 운용이 들어가는 순간 이 논리 붕괴.

## 6. 구조화채권 토크나이제이션 MVP 설계

### 컨셉
```
스마트컨트랙트 = 계약서
(BCC, Day Count Fraction, Payoff, Notional, Settlement Currency 하드코딩)

투자자 매수 → 토큰 수령
쿠폰지급일 → 컨트랙트가 자동 USDC 지급
만기 → 원금 자동 상환
```

### Reserve 구조
- 발행자 Reserve 지갑 잔액 온체인 공개
- 다음 쿠폰지급일까지 최소 Reserve = 다음 쿠폰 지급액
- 만기 가까워질수록 Reserve 최소잔액 증가
- Reserve 부족 시 → 운용 지갑 거래내역 자동 공개 트리거

### 투명성 설계
- KYC/KYB 완료 → 지갑 주소-실명 매핑 공개
- 발행자 Reserve 지갑: 항상 공개
- 운용 지갑: Reserve 충분하면 비공개, 부족하면 자동 공개

### 기존 AllowanceVault와의 관계
AllowanceVault 뼈대(ERC-721 NFT = 청구권)를 재활용하여 확장:

| AllowanceVault | 구조화채권 컨트랙트 |
|----------------|-------------------|
| 수시 적립 | 쿠폰지급일 자동 지급 |
| NFT 보유자 claim | 지급일 도래 시 자동 or claim |
| 잔액 확인 | Reserve 현황 + 최소 Reserve 계산 |
| 없음 | Day Count, Notional, Coupon Rate |
| 없음 | Reserve 부족 시 운용지갑 공개 |

### 테스트 스펙
- 만기: 1주일
- Day Count: 30/360 단순화
- 쿠폰: 만기에 원금+이자 일괄 지급 (1주일이므로)
- 체인: Ethereum Sepolia
- 토큰: ERC-721 (기존 EMILIO-BOND 뼈대)
- 발행자 본인 자금으로 Reserve 채움
