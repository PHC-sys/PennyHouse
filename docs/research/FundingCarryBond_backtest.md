## 2. 백테스트 설정

| 항목 | 값 |
|------|-----|
| 데이터 소스 | Hyperliquid `fundingHistory` API |
| 조회 기간 | 180일 (페이지네이션, 최대 500건/회) |
| 코인 | BTC, ETH, HYPE |
| 만기 | 30일 |
| 쿠폰 지급일 | Day 21, Day 28 (3주차·4주차) |
| 목표 APY | 8.0% |
| Reserve 비율 | 5%, 10%, 20% 비교 |
| 레버리지 | 1x, 2x, 3x |
| 수수료 | 왕복 8.5bp (Spot Maker 0.04% + Perp Taker 0.045%, 노셔널 절반씩) |

### 수수료 산출 근거

```
노셔널 = TOTAL_CAP × L / (1+L)
  → Spot과 Perp 각각 노셔널의 절반씩 사용
  
1회 수수료 = (Spot Maker 0.040% + Perp Taker 0.045%) × 노셔널
왕복 수수료 = 위의 2배

예) 1x, TOTAL_CAP=1.20: 노셔널=0.60, 왕복=10.20bp
```

### 펀딩 수익 계산 (핵심 수정사항)

```
기존 (잘못된) 계산:
  funding = fundingRate × HOURS_PER_TICK × leverage × TOTAL_CAP

올바른 계산:
  notional = TOTAL_CAP × L / (1+L)   ← 델타뉴트럴 실제 포지션
  funding  = fundingRate × HOURS_PER_TICK × notional

L=1: 펀딩 승수 = 0.50 (연 11% → 실효 5.5%)
L=2: 펀딩 승수 = 0.67 (연 11% → 실효 7.3%)
L=3: 펀딩 승수 = 0.75 (연 11% → 실효 8.25%)
```

## 4. 핵심 발견

### 4-1. 발행자 손익 분기 조건

```
펀딩레이트 × 노셔널 > 쿠폰 × P + 수수료

L=1 기준:
  (펀딩 × 0.5 × TOTAL_CAP) > (APY × 30/365 × P) + 수수료
  → 펀딩 > APY / 0.5 = 16% 이상 필요  ← 현재 BTC는 불가
  
L=3 기준:
  (펀딩 × 0.75 × TOTAL_CAP) > (APY × 30/365 × P) + 수수료
  → 펀딩 > 10.7% 이상 필요  ← HYPE(12%)는 가능
```

### 4-2. Reserve 비율의 역설

Reserve를 낮추면 절대 손실은 같아도 % ROI는 더 나빠 보임.  
Reserve 비율은 투자자 신뢰 / 안전마진 / 발행자 진입 장벽의 균형점.

**권고**: 30일 만기 기준 최소 Reserve는 5~10% 수준으로 충분.  
`minReserve = 연이표 × 1.2` 공식은 전통 채권 구조에서 온 것으로 이 구조에 부적합.

### 4-3. 리밸런싱 비용 미반영

현재 백테스트는 중간 리밸런싱 비용 미포함.  
BTC 가격 10% 변동 시 추가 수수료 ≈ 0.004% — 30일 마진을 고려하면 무시 가능하나,  
Bull/Bear 전환 시에는 영향 있음.

## 5. 결론 및 보류 이유

### 동작하는 조건

| 조건 | 판단 |
|------|------|
| HYPE 2x~3x, 펀딩 12%+ | ✅ 발행자 연 12~17% ROI |
| ETH 3x, 펀딩 9%+ | ✅ 발행자 연 11% ROI |
| BTC, 펀딩 7~8% | ❌ 8% 쿠폰 구조에서 발행자 손해 |

### 보류 이유

1. **펀딩레이트가 쿠폰을 못 따라가는 구간이 반드시 온다**  
   Bear 장, 역펀딩 기간에는 구조적 손실

2. **고정 쿠폰이 발행자에게 리스크를 집중시킴**  
   투자자는 안전하지만, 발행자는 시장 변동에 무방비

3. **구현 복잡도 높음**  
   CoreWriter + 2-Phase Commit + Keeper = 버그 리스크

4. **유사 프로토콜 존재**  
   Hyperbeat, Harmonix가 동일 전략을 더 단순하게 운용 중
