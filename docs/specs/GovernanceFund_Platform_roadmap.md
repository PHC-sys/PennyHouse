## 0. 비전 & 원칙

투표로 운용하는 사모 거버넌스 펀드의 **백테스트·페이퍼 트레이딩·실펀드** 플랫폼.
블룸버그 터미널급 정보 밀도 + 모던 DeFi 서비스(Hyperliquid/GMX/Pendle)급 폴리시.

### 핵심 설계 원칙
1. **API 우선(API-first)** — 모든 로직은 FastAPI 백엔드. 프론트는 소비자.
   → 웹(Next.js) 완성 후 **모바일 앱**(React Native/Expo 또는 Flutter)이
     동일 `/api/*`를 재사용. 클라이언트만 추가하면 됨.
2. **반응형 우선** — 컴포넌트를 모바일 뷰포트까지 고려해 설계 (앱 전환 대비).
3. **엔진 단일화** — `governance/engine`이 백테스트·페이퍼·실펀드·Keeper의 공통 두뇌.
4. **검증 우선** — 모든 수치 로직은 자체 테스트(assert)로 검증 후 반영.

## 3. 핵심 계산식 (검증 기준)

### 3-1. 펀딩 캐리 (HL 공식)
```
funding_payment = position_notional × funding_rate
position_notional = |수량| × mark_price = (비중/100) × equity × leverage

연환산 캐리(equity 대비 %) = Σ_coin [ -(비중/100) × leverage × funding_annual ]
  롱(+비중): 펀딩>0 이면 지불(−)
  숏(−비중): 펀딩>0 이면 수취(+)
```
- **레버리지 곱하는 게 정상** (노셔널 기준이므로). 큰 값이 나오는 건 버그 아님.
- 표기: "현재 펀딩레이트가 1년 유지 가정", equity 대비 %임을 명시.
- 정확도 향상: HL 펀딩 정산 주기(8시간)를 페이퍼에 반영.

### 3-1b. 자산별 수익 기여도 (리밸런싱 정합)
```
매 시점 코인별로 따로 적립 (그 시점 비중으로 그 구간 손익):
  asset_pnl[coin] += (weight[coin]/100) × equity × lev × daily_return[coin]

펀드 총 수익 = Σ asset_pnl[coin]          (= 기존 NAV 수익과 일치해야 함)
코인별 기여도(%) = asset_pnl[coin] / 초기자본 × 100
```
- 비중이 롱→숏 전환돼도 부호가 자동 처리 → 구간별로 정확히 합산됨.
- 백테스트·페이퍼 양쪽 동일 적용. 펀딩캐리도 코인별로 분리해 "가격손익 + 펀딩"
  합쳐 보여주면 터미널급 정보 밀도.

### 3-2. 평균단가 / 청산가 (페이퍼용)
```
평균단가 = Σ(체결가 × 수량) / Σ수량   (리밸런싱마다 갱신)

청산가 (HL isolated 근사):
  롱: liq = entry × (1 − 1/lev + mmr)
  숏: liq = entry × (1 + 1/lev − mmr)
  mmr(유지증거금률) = 자산별 (HL meta의 maxLeverage로 산출)
청산까지 거리(%) = |현재가 − liq| / 현재가 × 100
```
- HL `meta`의 자산별 `maxLeverage`로 mmr 추정 → 실제 청산가 괴리 최소화.

## 4. 빌드 순서 (단계)

```
1차 — 즉효 (작음)  ✅ 완료
  ✅ 펀딩 캐리 표기 정직화 + 라벨 명확화 (현재 펀딩 1년 유지 가정)
  ✅ 자산별 수익률 — 코인별 PnL 누적 적립 (리밸런싱 구간별 합산)
  ✅ 1x(spot) 레버리지 프로파일 추가
  ✅ 페이퍼: 평균단가·청산가·청산거리 (HL meta maxLeverage→mmr)

2차 — 데이터 기반 (중간)  ✅ 완료
  ✅ HL 전 자산 레지스트리 (메인 dex 크립토 + HIP-3 xyz/vntl)
     → 265개 (크립토179 + TradFi73 + Pre-IPO13), 자동 카테고리 분류
  ✅ 변동성 자동 계산 (compute_volatility)
  ✅ 마켓 탭: 블룸버그식 타일 + 자산 상세 모달(캔들 OHLC호버/펀딩/상대가격)
  ✅ 마켓 폴리시: ⌘K 커맨드 팔레트, 즐겨찾기(★), 거래량/OI
  ✅ 로딩 최적화: _post 동시성제한+재시도, 배치 스파크, IntersectionObserver
     점진적 렌더(숫자 즉시 + 보이는 타일만 lazy + 페이드인)
  ✅ 펀딩/캔들 페이지네이션 (730일), prefix(xyz:NVDA) 라우팅

2.5차 — 라이브 데이터 (다음)  ← 현재
  □ HL WebSocket 수집 워커 (서버 1개): allMids 현재가 + candle 마지막봉
  □ 서버 메모리 스토어 (현재가/펀딩 최신값) — HL 호출을 워커 1곳으로 집중
  □ FastAPI WebSocket(/ws/market) → 브라우저에 변경분 푸시
  □ 프론트: 마켓 타일 숫자 틱 갱신(녹/빨 플래시), 모달 캔들 마지막봉 update()
  ※ "라이브 + 가벼움": 차트는 전체 재로딩 X, 마지막 봉만 update

3차 — 구조 변경 (큼)
  □ SQLite 도입 (펀드별 상태/투표/NAV 영속화)
  □ 펀드 개설 폼: 이름·가상예치금·최대한도·Public/Private·허용지갑·
     운용 유니버스(자산 선택)·초기 비중·레버리지
  □ 펀드 목록 + 입장

4차 — 게임형 (멀티펀드 위)
  □ 리플레이 모드: 과거 시점 시작 → 구간별 공개 → 투표 → 진행 →
     최종 성적 + Perfect 대비 점수

5차 — 접근 제어 (마지막)
  □ 지갑 서명 인증 → Private 펀드 접근 제어
```

> 각 차수는 독립 커밋·검증. 무리하면 차수 내에서도 끊어서 진행.

## 4.5 라이브 데이터 아키텍처 (2.5차)

### 문제 (현재)
```
브라우저 → FastAPI → HL REST (화면 열 때마다 직접 호출)
→ 느림, rate limit, 캐시로 땜빵. 화면마다 HL 찌르는 구조.
```

### 목표 구조 (Fan-out)
```
[수집 워커 1개]  HL WebSocket 구독 → 서버 메모리 스토어 갱신
                   (allMids 현재가, 구독된 candle 마지막봉)
        ↓
[FastAPI]  REST: 메모리 읽기 (HL 안 찌름) / WS: 변경분 푸시
        ↓
[브라우저 N명]  서버 메모리만 봄 → HL 호출은 워커 1곳뿐 → 가볍다
```

### "라이브 + 가벼움"의 선
| 데이터 | 무게 | 라이브 방식 |
|--------|------|-------------|
| 현재가/등락/펀딩 | 가벼움(숫자) | 틱마다 갱신 + 녹/빨 플래시 |
| 캔들 차트 | — | **마지막 봉만 `series.update()`** (전체 재로딩 X) |
| 스파크라인 | — | 마지막 점만 갱신(선택) |

→ 차트도 라이브지만 "통째 재그리기"가 아니라 진행 중인 봉 1개만 갱신 → 부드러움.

### 저장소 정책
- 현재가/펀딩 최신값 = **메모리 딕셔너리** (가장 가벼움)
- 영속 데이터(펀드 상태 등) = **SQLite** (3차에서 도입)
- Redis 등은 실제 트래픽 발생 시 검토 (현 단계 과함)

### HL WebSocket
- 엔드포인트: `wss://api.hyperliquid.xyz/ws` (무료, 공개데이터 무인증)
- 구독: `allMids`(전 자산 mid), `candle`(coin+interval), `activeAssetCtx`(펀딩 등)

## 5. 모바일 앱 대비 (선행 고려사항)

- API 응답을 클라이언트 무관하게 설계 (HTML 조각 X, 순수 JSON O) — 이미 준수.
- 인증은 토큰/서명 기반으로 (쿠키 세션 의존 X) → 앱에서 재사용 용이.
- 차트: 웹은 lightweight-charts, 앱은 동일 데이터로 네이티브 차트 라이브러리.
- 디자인 토큰(색/타이포/여백)을 문서화 → 앱과 룩앤필 공유.

## 6. 자산 유니버스 정책

- HL `meta`에 상장된 **전 perp**를 목록으로 제공 (Crypto + TradFi + Pre-IPO).
- 단, 펀드는 그중 **운용 유니버스(예: 5~15종)**를 선택 — 백테스트 성능·UX 위해.
- HL에 없는 자산(개별 미국주식 등)은 현 단계 제외 (실펀드 운용 불가 괴리 방지).
