# GovernanceFund — 사모 거버넌스 투자 펀드 스펙

> 작성일: 2026-06-10  
> 상태: 설계 중 (v0.1 개념 확정)  
> 분류: 신규 핵심 방향

---

## 1. 개념 요약

지인 간 폐쇄형(사모) 암호화폐 투자 펀드.  
참여자가 투표로 포트폴리오 전략을 결정하고,  
AI Keeper가 투표 결과를 자동으로 실행 (Hyperliquid REST API 기반).

**한 줄 정의**: 폴리마켓과 Hyperliquid 사이 어딘가 — "내기 감각"으로 포트폴리오를 직접 운용.

---

## 2. 배경 및 동기

### 왜 만드나

- 한국 투자자는 증권거래소를 통해 접근할 수 없는 자산이 많음  
  (원자재 선물, FX, Pre-IPO, 해외 크립토 파생 등)
- 기존 펀드는 운용사가 결정 → 투자자는 수동적
- 친구들끼리 각자의 인사이트를 합쳐 운용하고 싶다
- 투표 가중치는 돈이 많이 들어간 사람이 더 가져가는 것이 합리적

### 왜 지금인가

- 부장님(시드 투자자) 참여 확정
- TVL이 작을 때 실험하고 검증하기 좋음
- AI Keeper가 중재자 역할 → 인간 분쟁 최소화

## 3. 핵심 메커니즘

### 3-1. 투표 → 포트폴리오 연결 (검증 완료)

> 백테스트 노트북(01·02번)과 검증 스크립트(`_verify_*.py`)로 전 과정 검증됨.

**1단계: 방향성 투표 (Kahoot 스타일)**
```
참여자는 코인별로 방향 하나만 선택:
  -2(강한 숏) / -1(숏) / 0(유지) / +1(롱) / +2(강한 롱)
→ 비중 숫자 입력 불필요, 3초면 끝
```

**2단계: 예치금 가중 집계 (simulate_votes)**
```
score[coin] = Σ(개인 투표 × 개인 예치금비중) / 2   (-1 ~ +1)
→ 돈 많이 넣은 사람 표가 더 셈
```

**3단계: 목표 비중 산출 (votes_to_target) — Target 방식**
```
target[coin] = score × vol_factor       # 방향+크기 즉시 결정 (부호=롱/숏)
정규화: sum(abs) = 100                   # gross exposure 100%
vol_factor = 0.03 / 코인변동성           # 변동성 큰 코인은 작게

※ 증분(누적) 방식은 방향 전환이 3~4주 걸려 폐기.
  Target 방식은 score가 곧바로 목표 → 숏도 즉시 진입 가능.
```

**4단계: 적응형 EMA 수렴 (투표주기 반비례 alpha)**
```
alpha = 1 - 0.1 ^ (투표주기 / 목표수렴기간T)
  주간 투표 → alpha 높음(0.9): 이번 주에 확 반영
  일간 투표 → alpha 낮음(0.28): 살살 반영하되 매일 누적
  → 어떤 주기든 '달력 기준 T일 안에 90% 수렴' 보장 (검증됨)

new_weight = alpha × target + (1-alpha) × current
```

**5단계: AI Keeper 실행**
```
현재 포지션 vs 목표 비중 diff 계산
→ HL REST API로 리밸런싱 (지정가 추격 + 타임아웃 → 시장가 폴백)
→ 슬리피지/가스 최소화
```

#### 핵심 파라미터 (프로파일별)
| 파라미터 | 공격적 | 보수적 | 의미 |
|----------|--------|--------|------|
| T_CONVERGE | 7일 | 21일 | 목표 비중 90% 도달 기간 |
| MAX_WEIGHT | 80% | 60% | 코인 1종 최대 비중(롱/숏 공통) |
| FUND_LEVERAGE | 5x | 2x | 전체 레버리지 |

### 3-2. AI Keeper 역할

- 투표 결과 읽기 (온체인 또는 오프체인 집계)
- 현재 포트폴리오 상태 조회 (HL REST API)
- 목표 비중 달성을 위한 최적 주문 생성
- 주문 실행 (리밸런싱)
- 결과 리포트 생성 (참여자 공유)

**핵심**: Keeper는 투표 결과를 "구속력 있게" 실행 — 사람이 개입해서 바꾸는 것이 불가 (또는 명시적 거부권 필요)

## 4. 아키텍처 개요

```
[웹/앱 프론트엔드]
  참여자 로그인 (지갑 연결)
  잔액 / 수익 현황 조회
  투표 UI (슬라이더로 비중 입력)
       ↓
[투표 집계 레이어]
  온체인 또는 오프체인 (초기: 오프체인 DB)
  가중치 계산 (예치금 비례)
  확정 투표 → AI Keeper에 전달
       ↓
[AI Keeper]
  HL REST API (포트폴리오 상태 조회)
  리밸런싱 주문 생성 (diff 계산)
  HL REST API (주문 실행)
  실행 결과 → 리포트 DB 저장
       ↓
[Hyperliquid]
  Spot / Perp 포지션
  자금 보관 (HL 계정)
       ↓
[프론트엔드]
  리밸런싱 내역 표시
  수익/손실 실시간 반영
```

## 5. UI 화면 구성 (3-Screen MVP)

### 화면 1: 대시보드
```
- 총 TVL / 내 예치금 / 내 지분율
- 포트폴리오 현황 (파이차트)
- 최근 수익률 (1주, 1달)
- 다음 투표 예정일
```

### 화면 2: 투표
```
- 자산별 비중 슬라이더 (합계 100%)
- 현재 투표 집계 현황 (익명 또는 공개 — 결정 필요)
- 내 투표 제출 / 수정
- 투표 마감까지 남은 시간
```

### 화면 3: 내역
```
- 리밸런싱 이력 (일시, 변경 내용, 수수료)
- 투표 이력
- 입출금 이력
```

## 7. 리스크 및 제약

### 규제 리스크
- 한국 자본시장법상 "집합투자" 해당 가능성  
  → 사모(49인 이하, 고액투자자) 구조로 규제 회피 검토
- 공개 모집 금지 — 완전 폐쇄형 유지 필수

### 기술 리스크
- HL REST API 다운 시 Keeper 멈춤 → 알림 + 수동 override 필요
- 슬리피지 관리: TVL이 커지면 시장 충격 고려한 분할 주문 필요
- Keeper 키 보안: Private key 관리 방식 결정 필요 (HSM vs 멀티시그)

### 운영 리스크
- 의사결정 속도: 가중치 분산 시 급변 대응 느림
- 책임 소재: 투표대로 실행했는데 손실 → 누구 책임?  
  → 투표 기록 온체인 보존으로 "각자 책임" 명문화

### FundingCarryBond와의 차이
- FundingCarryBond: 발행자가 전략 결정, 투자자는 고정금리만 받음
- GovernanceFund: 투자자가 직접 전략 결정, 수익/손실 모두 공유

## 8. 마일스톤 (초안)

```
Phase 0 — 개념 검증 (현재)
  ✅ 개념 설계
  ✅ 경제 구조 합의
  □ 참여자 확보 (목표: 3~5명, 시드 자금 확정)

Phase 1 — MVP (오프체인)
  □ 단순 웹 UI (대시보드 + 투표)
  □ AI Keeper 프로토타입 (HL API 연동)
  □ 오프체인 투표 집계 (DB)
  □ 소액 실운용 테스트

Phase 2 — 온체인 투표
  □ 투표 스마트컨트랙트 (Arbitrum or HyperEVM)
  □ 예치금 컨트랙트 (지분 토큰화)
  □ Keeper → 컨트랙트 연동

Phase 3 — 확장
  □ 모바일 앱
  □ 전략 다변화 (DeFi 프로토콜, 외부 LP 등)
  □ FundingCarryBond 레이어 통합 검토
```

## 9. FundingCarryBond와의 연결 가능성

GovernanceFund TVL이 충분히 확보된 이후:
- 일부 자금을 FundingCarryBond 전략에 배분 (투표로 결정)
- GovernanceFund 내부에서 채권을 발행 → 외부 투자자 모집
- Keeper가 채권 만기/쿠폰도 관리

→ 장기적으로 GovernanceFund가 FundingCarryBond의 운용 주체가 될 수 있음.
